Carpenter Campaign Management & Attendance Verification — Flutter Architecture

A single Flutter codebase spanning the mobile field app, web campaign administration, CRM verification console, and management analytics — extending the existing Sales Ecosystem shell.

Status · Proposed 2026-07-26 Owner · Asim Ibne Ilyus Basis · PRD Draft + UI/UX Guideline v1.0
Key architecture decision

One Flutter codebase for all four surfaces

Flutter targets Android/iOS for offline-first field capture and Flutter Web for the admin, CRM, and analytics consoles. This maximizes cross-surface consistency — the same status vocabulary, validation, and design tokens everywhere, a non-negotiable requirement of the guideline. The accepted trade-off is Flutter Web's accessibility and dense-table effort, which are mitigated deliberately (§6) and treated as a release gate, not polish.

04

Web Strategy & Sensitive-Data Handling

Mitigating the accepted Flutter-Web trade-offs, and the client's share of privacy enforcement.

WEB · A11Y

WCAG 2.2 AA as a release gate

Semantics wrappers on all controls, keyboard focus + shortcuts for CRM, contrast enforced by tokens, screen-reader audits every sprint.

WEB · TABLES

One virtualized BmdDataTable

Sticky header + identity column, 44–48px rows, safe bulk-select. Reused by list, import, CRM queue, 360, analytics.

PRIVACY

Sensitive media

Signed short-lived URLs, blurred thumbnails until authorized open, download off by default, every view audited.

PRIVACY

NID & scores

NID masked to suffix, reveal permission-gated + audited. Field users see no match score; CRM sees band + reasons only.
